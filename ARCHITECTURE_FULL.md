# Полное описание архитектуры PugErm

## 1. Назначение решения

PugErm — это explainable AI-прототип для Case 2 хакатона Decentrathon 5.0. Система предназначена для поддержки комиссии при рассмотрении заявок на субсидии в сельском хозяйстве.

Цель решения:
- перейти от механики "first come, first served" к data-driven приоритизации;
- показать shortlist кандидатов для рассмотрения;
- объяснить, какие факторы повлияли на score каждой заявки;
- сохранить за человеком окончательное решение.

Система не заменяет эксперта и не является единственным источником истины.

## 2. Архитектурный подход

Архитектура построена как лёгкий модульный прототип из трёх основных слоёв:

1. Слой представления
2. Сервисный API-слой
3. ML-слой скоринга и explainability

Такой подход позволяет быстро показать рабочий MVP на первом этапе и при этом не блокирует масштабирование на следующих стадиях.

## 3. Основные компоненты

### 3.1 Frontend

Файлы:
- `web/index.html`
- `web/app.js`
- `web/styles.css`

Назначение:
- загрузка XLSX/CSV;
- запуск анализа;
- отображение summary по данным;
- показ shortlist для комиссии;
- отображение глобальных факторов модели;
- отображение локальных факторов для каждой записи;
- отображение используемых и исключённых полей.

Пользовательский сценарий:
1. пользователь открывает веб-интерфейс;
2. загружает файл или запускает demo на `Data.xlsx`;
3. получает список заявителей с score и объяснениями.

### 3.2 Backend API

Файл:
- `cmd/server/main.py`

Назначение:
- отдача фронтенда;
- приём запроса `POST /api/score`;
- временное сохранение загружаемого файла;
- вызов ML-скрипта как отдельного процесса;
- возврат JSON-результата во frontend.

Почему выбран такой подход:
- простая и прозрачная интеграция;
- независимость frontend и ML-логики;
- удобство демонстрации на хакатоне;
- возможность позднее вынести ML в отдельный сервис.

### 3.3 ML Scoring Engine

Файл:
- `ml/score.py`

Назначение:
- чтение данных из XLSX/CSV;
- очистка пустых строк и столбцов;
- исключение технических полей и идентификаторов;
- подготовка числовых и категориальных признаков;
- расчёт score;
- расчёт global factors и local factors;
- формирование shortlist.

Текущий режим работы:
- supervised, если во входных данных есть корректная target-колонка;
- unsupervised prototype ranking, если target отсутствует.

Это позволяет показать рабочий прототип даже на неполном или раннем датасете.

## 4. Источники данных в архитектуре

### 4.1 Текущий демонстрационный источник

- `Data.xlsx`

Используется как основной демонстрационный источник для Stage 1.

### 4.2 Изученные дополнительные материалы

- `Выгрузка по выданным субсидиям 2025 год (обезлич).xlsx`
- `Правила субсидирования развития племенного животноводства, повышения продуктивности и качества продукции животноводства.pdf`

Роль этих материалов:
- подтверждают реальную предметную область;
- показывают структуру реестровых данных и нормативную основу;
- служат следующими источниками для обогащения модели и добавления rule-alignment слоя.

Важно:
на текущем этапе они используются как доменные материалы для проектирования и развития решения, а не как полностью интегрированный production-ready pipeline.

## 5. Поток данных

Полный поток обработки:

1. Пользователь загружает файл через frontend.
2. Frontend отправляет запрос в `POST /api/score`.
3. Backend принимает файл и подготавливает его для обработки.
4. Backend запускает `ml/score.py`.
5. ML-модуль:
   - считывает данные;
   - очищает таблицу;
   - исключает технические поля;
   - подготавливает признаки;
   - рассчитывает score;
   - формирует shortlist;
   - считает объяснения по факторам.
6. Backend получает JSON-ответ.
7. Frontend визуализирует результат для комиссии.

## 6. Explainability в архитектуре

Explainability заложен как обязательный слой результата.

### Глобальная explainability

Показывает наиболее влиятельные признаки на уровне всей выборки.

Примеры:
- норматив;
- направление субсидирования;
- тип программы;
- региональные характеристики.

### Локальная explainability

Показывает top factors для конкретной заявки:
- какие факторы повысили score;
- какие факторы понизили score.

### Техническая explainability

Во frontend дополнительно показываются:
- используемые поля;
- исключённые поля;
- причины исключения технических колонок.

Это важно для прозрачности перед комиссией и жюри.

## 7. Роль человека в принятии решения

Архитектура соответствует ограничению из ТЗ:
- AI не принимает окончательное решение автоматически;
- AI формирует shortlist и объяснение;
- окончательное решение остаётся за комиссией или экспертом.

Это отражено:
- в интерфейсе;
- в логике shortlist;
- в документации проекта.

## 8. Почему эта архитектура подходит для Stage 1

Для первого этапа требуется:
- репозиторий с кодом;
- описание архитектуры;
- минимально рабочий элемент.

Текущая архитектура это закрывает, потому что в проекте уже есть:
- работающий frontend;
- backend API;
- ML-модуль;
- explainable output;
- демонстрационный сценарий на `Data.xlsx`.

## 9. Текущие ограничения архитектуры

- пока нет постоянного хранения результатов;
- нет БД и истории запусков;
- нет очереди фоновой обработки;
- нет авторизации и ролей пользователей;
- текущая модель зависит от структуры входного датасета;
- интеграция нормативных правил пока концептуальная, а не полная;
- дополнительные реальные выгрузки требуют отдельного слоя нормализации входных данных.

## 10. План масштабирования

На следующих этапах архитектура может быть расширена следующим образом:

### 10.1 Нормализация входных данных

Добавить слой `Data Adapter`, который:
- распознаёт формат выгрузки;
- корректно поднимает заголовки;
- унифицирует типы колонок;
- приводит разные выгрузки к общей схеме признаков.

### 10.2 Rule Layer

Добавить слой нормативной логики на основе PDF-правил:
- проверка соответствия программы заявленному направлению;
- валидация нормативных ограничений;
- rule flags и risk markers для комиссии.

### 10.3 Feature Store / Enrichment

Добавить объединение:
- истории субсидий,
- производственных показателей,
- географических и отраслевых признаков.

### 10.4 Persistent Storage

Добавить хранилище:
- версий модели,
- результатов скоринга,
- объяснений,
- audit trail.

### 10.5 Export and Decision Support

Добавить:
- экспорт shortlist;
- режим сравнения заявителей;
- журнал экспертного решения;
- флаги риска и рекомендаций.

## 11. Краткий вывод

PugErm построен как модульный explainable AI-прототип:
- простой для демонстрации;
- достаточный для Stage 1;
- масштабируемый на Stage 2 и финал;
- совместимый с дальнейшей интеграцией реестровых данных и нормативных правил.
